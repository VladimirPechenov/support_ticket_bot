# Telegram Support Ticket Bot

Демонстрационный проект Telegram-поддержки на TypeScript и Node.js: обращения,
AI-ответы и передача диалога оператору. Репозиторий подготовлен для просмотра
кода и запуска изолированной демонстрации.

Реальные ключи, данные пользователей, рабочая база знаний, сетевые настройки
и материалы прежнего сервиса в эту версию не входят. Шесть записей в
`test/fixtures/knowledge-base.jsonl` полностью вымышлены и нужны для тестов.

## Что посмотреть в коде

- `src/ai.ts`: обработка сообщений, владение активным запросом и отмена AI
  при вмешательстве оператора; защита от отправки устаревшего ответа.
- `src/full-knowledge-agent.ts`: структурированное решение reply/handoff
  с контекстом, который предоставляет владелец установки.
- `src/ai-client.ts`, `src/ai-provider.ts`: бюджеты времени и попыток,
  резервный провайдер, квоты, circuit breaker и отмена запросов.
- `src/lexical-retriever.ts`, `src/rag-ranking.ts`: лексический поиск,
  BM25, опечатки и объединение результатов с векторным поиском.
- `src/staff-panel.ts`, `src/staff-card.ts`: очередь, карточки и действия
  операторов с проверкой доступа.
- `src/db.ts`: SQLite, миграции, история обращений и технические события.
- `src/verified-docs.ts`: чтение только разрешённых HTTPS-источников,
  контроль адресов и кеш. В демонстрации выключено; example.com — заглушка.
- `src/logger.ts`, `src/health-server.ts`: фильтрация журналов, health,
  readiness и метрики.

## Основа и развитие

Проект основан на открытом [telegram-support-bot v4.1.1](https://github.com/bostrot/telegram-support-bot/tree/v4.1.1).
Исходная версия предоставила базовые Telegram-обращения и ответы сотрудников.
В адаптации расширены AI-сценарии, поиск, передача оператору, постоянное
хранение состояния, операторский интерфейс, диагностика и тесты.
Использовались AI-инструменты разработки; сценарии и результат проверялись
вручную и автоматическими проверками. Лицензия — GPL-3.0, см. LICENSE и NOTICE.

## Быстрая проверка без токенов

Нужны Node.js 22+ и npm. На платформах без готового бинарного модуля
better-sqlite3 также потребуются Python и инструменты C++.

```sh
npm ci
npm run verify:public
npm run check
npm run build
npm test
```

Тесты создают отдельные временные SQLite, настройки и журналы; API-ключи
из окружения не передаются. Существующие настройки не перезаписываются.
Внешние AI API в автоматических тестах подменены. Рабочий Telegram-бот
и Qdrant для этого набора тестов не нужны.

## Локальная демонстрация в Telegram

```sh
npm run demo:setup
```

Команда создаёт игнорируемые Git файлы `.env`, `config/config.yaml` и
`config/knowledge-base.jsonl`, если они ещё не существуют. Заполните свой
BOT_TOKEN в `.env`, owner_id и staffchat_id в YAML. Используйте отдельного
тестового бота и свою группу поддержки. Затем:

```sh
npm run build
npm run config:check
npm run prod
```

По умолчанию AI выключен: обращения обрабатывает оператор. Для режима `full`
нужны собственный ключ выбранного провайдера, подходящая модель, ваша база
знаний, режим `full` и разрешённый rollout. Фактические флаги сохраняются
в SQLite и управляются командами `/aictl` и `/aihealth`; изменения YAML
не перезаписывают уже сохранённый режим. Живые API-вызовы расходуют квоты.

Режим `full` передаёт всю базу модели. Режим `rag_only` выбирает готовую
инструкцию; для векторного поиска нужны Qdrant и embeddings. Не называйте
передачу всей базы retrieval: это разные сценарии с разными ограничениями.

Для своей базы используйте `config/knowledge-base.jsonl` или SUPPORT_KB_PATH.
Каждая строка — JSON-объект с полями id, title, answer, aliases, tags, source,
updated_at. Тестовые примеры не являются документацией реального сервиса.

## Docker

После настройки локальных файлов:

```sh
docker compose up --build supportbot
```

Опциональный Qdrant: `docker compose --profile rag up -d qdrant`.
Каталоги config и logs должны быть доступны пользователю node контейнера.
Прокси, реальные хосты и старые deployment-скрипты в демонстрацию не включены.

## Ограничения

- Это портфолио-версия, а не готовый production-сервис и не публичная AI-демка.
- Набор тестов проверяет поведение кода с синтетическими данными; он не
  подтверждает качество конкретной модели или доступность её API.
- Для своей установки нужно настроить права, источники, модели и проверить
  пользовательские сценарии. Рабочую SQLite и журналы не коммитить.

На Windows права доступа к файлам определяются ACL. Если используются baseline-артефакты RAG, ограничьте доступ к их каталогу; проверка POSIX-битов применяется на Linux/macOS.

Проверка `verify:public` анализирует текущие отслеживаемые файлы и не печатает найденные значения. Она не заменяет проверку всей истории и отзыв уже раскрытых ключей. Два унаследованных теста старого интерфейса помечены как пропущенные; основной поток обращений и действия оператора покрываются отдельными проверками.
